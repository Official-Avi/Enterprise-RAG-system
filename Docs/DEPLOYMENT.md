# Development and Deployment Plan

Sections 1 to 7 are the deployment plan and its goals. They do not describe what exists. Section 8 is
what is implemented, and it says what has been executed. **RackFlow AI has never run in production or
staging, and nothing here claims it is ready to.**

For a production install, follow [`PRODUCTION_CHECKLIST.md`](PRODUCTION_CHECKLIST.md) step by step. It
links to `deploy/README.md` (Compose overlay and Caddy) and `scripts/ops/README.md` (backups).

## 1. Development environment
Docker Compose runs:
- web frontend,
- API,
- background worker,
- PostgreSQL (metadata and the job queue; there is no Redis or other broker, see ADR-005),
- Qdrant.

Object storage is a local volume. The Windows development host has no Docker and runs PostgreSQL and
Qdrant from portable binaries (§8.4).

The model runtime is optional, so the application boots without one: the default `extractive` provider uses no LLM. The backend test suite runs with that provider and a `hash` test embedder.

## 2. Environment variables
Create `.env.example` documenting names and safe placeholders, for example:
- `APP_ENV`
- `API_BASE_URL`
- `DATABASE_URL`
- `VECTOR_STORE_URL`
- `OBJECT_STORAGE_MODE`
- `OBJECT_STORAGE_ENDPOINT`
- `OBJECT_STORAGE_BUCKET`
- `MODEL_PROVIDER`
- `MODEL_NAME`
- `MODEL_BASE_URL`
- `MODEL_API_KEY` (placeholder only; never commit real value)
- `EMBEDDING_PROVIDER`
- `EMBEDDING_MODEL`
- `UPLOAD_MAX_BYTES`
- `JOB_MAX_ATTEMPTS`
- `LOG_LEVEL`
- `AUTH_ISSUER` (reserved; no OIDC provider exists yet)
- `DEMO_MODE` (default false; refused with `APP_ENV=production`)
- `TRUSTED_PROXY_IPS` (default empty; see §8.8)
- `MODEL_TIMEOUT_SECONDS`, `WEB_PROXY_TIMEOUT_SECONDS` (see §8.9)
- `VECTOR_STORE_API_KEY` (production: required for a remote Qdrant, and by the Compose overlay)

Production values are documented in `deploy/env.production.example` and generated by
`scripts/ops/generate_env.py` (§8.2).

Validate required variables at startup and fail with a safe, actionable message.

## 3. Local startup
The repository README must include exact commands based on the actual implementation. Expected outline:
1. Copy `.env.example` to `.env` and fill only local values.
2. Start dependencies with Compose.
3. Run database migrations.
4. Start API, worker, and web.
5. Open the local frontend and health endpoints.
6. Run smoke tests.
Do not write commands that have not been tested.

## 4. Staging
- Use separate tenant/data namespace and credentials from production.
- Enable TLS, managed database/object storage, backups, metrics, and central logs.
- The job queue lives in PostgreSQL, so it follows the database's durability and backups.
- Restrict admin access and apply rate limits.
- Configure model serving with explicit resource limits.

## 5. Production
- Deploy stateless API replicas behind a load balancer.
- Scale worker replicas separately according to queue depth and CPU/memory/OCR load.
- Scale model-serving replicas independently; test batching/concurrency and GPU/CPU fit.
- Use managed PostgreSQL with backup/PITR if available.
- Use durable object storage and lifecycle policies.
- Configure vector DB backups and tested restore.
- Use health/readiness probes and graceful shutdown.
- Roll out migrations with a documented backup/rollback plan.
- Monitor errors, queue age, processing latency, retrieval latency, model latency, saturation, and cost.

## 6. Resource reality
Do not promise a particular concurrency level until measured. A 0.5B model may be small, but serving 500 simultaneous engineers depends on hardware, request rate, prompt/output lengths, batching, quantization, runtime, and acceptable latency. Test on the actual target environment.

## 7. Deployment acceptance
- Clean install succeeds.
- Health and readiness are correct.
- Secrets are injected securely.
- Backups and restore are tested.
- Queue recovery and worker restart are tested.
- Dashboard values match backend metrics.
- Runbook covers common failures and rollback.

| Process | Command | Scales | State |

### 8.2 Environment variables and production rules (no secrets in images or the repository)
`.env.example` documents the development values; `deploy/env.production.example` documents every
production variable with placeholders only. Generate the real production file instead of copying:

```
python scripts/ops/generate_env.py --output .env --domain <DOMAIN> --tls-issuer <email|internal> [--db-host postgres] [--force]
```

It writes `APP_ENV=production`, `COOKIE_SECURE=true`, `DEMO_MODE=false`, `LOG_LEVEL=INFO`,
`WEB_ORIGIN`/`API_BASE_URL` = `https://DOMAIN` (empty without `--domain`, so the API refuses to start
until they are set), `MODEL_PROVIDER=extractive`, the Compose timeouts and
`TRUSTED_PROXY_IPS=172.30.0.10,172.30.0.11`, and two fresh `secrets.token_urlsafe(32)` values:
`POSTGRES_PASSWORD` (also in `DATABASE_URL`) and `VECTOR_STORE_API_KEY` (also as
`QDRANT__SERVICE__API_KEY`). It never overwrites without `--force`, creates the file with mode 600 on
POSIX (Windows: use ACLs), and prints names only. Exit 0 written, 1 file exists or unwritable, 2 bad
arguments. Tested by `backend/tests/test_generate_env.py`, which also checks the output validates as
production `Settings`. It does not write `RACKFLOW_ADMIN_PASSWORD`.

Secrets (`POSTGRES_PASSWORD`, `MODEL_API_KEY`, `VECTOR_STORE_API_KEY`) must come from the deployment's
secret store or this file, never from the repository or an image (both `.dockerignore` files exclude
`.env*` and `.data`).

**With `APP_ENV=production` the API refuses to start** (ADR-027; the error names the variable, never its
value; `hide_input_in_errors` keeps values out of every validation error) when:

| Variable | Refused |
| --- | --- |
| `COOKIE_SECURE` | false |
| `DEMO_MODE` | true |
| `EMBEDDING_PROVIDER` | `hash` (test only) |
| `DATABASE_URL` | unparseable; no password; password `rackflow`; password equal to the user name; password under 16 characters |
| `WEB_ORIGIN` | empty, or any origin that is not `https://` |
| `API_BASE_URL` | not `https://` |
| `VECTOR_STORE_URL` / `VECTOR_STORE_API_KEY` | not http(s); or a non-internal host without `https://` and a non-blank key |
| `MODEL_PROVIDER=openai_compatible` | blank `MODEL_NAME`, no `MODEL_BASE_URL` (all environments); in production a non-internal `MODEL_BASE_URL` without `https://` and `MODEL_API_KEY` |
| `MODEL_PROVIDER=anthropic` | blank or whitespace `MODEL_API_KEY` |
| `LOG_LEVEL` | `DEBUG` or `NOTSET`, any case |
| `MODEL_TIMEOUT_SECONDS` | not below `WEB_PROXY_TIMEOUT_SECONDS` |
| `TRUSTED_PROXY_IPS` | invalid, `*`, host names, `/0` (all environments) |

"Internal" is decided by name, without DNS: loopback and private IPs, `localhost`, single-label names such
as `qdrant`, and the suffixes `.localhost`, `.internal`, `.local`, `.lan`, `.home.arpa`, `.svc`,
`.cluster.local`. Production also hides the API docs (`/api/v1/docs` and `openapi.json` return 404).

Choosing a remote model sends each question, the matched passages and, for a follow-up, one earlier
question to that provider (ADR-023). Decide this deliberately for each deployment.

### 8.3 Docker Compose (Linux): development stack — verified in CI at v0.1.0 only
`docker compose up --build` with no profile and no overlay is the **development** stack: PostgreSQL,
Qdrant, the migration job, API, worker and web, plain HTTP, every port on 127.0.0.1. CI job
`compose-smoke` builds both images, runs `docker compose up -d --build --wait`, and checks liveness,
readiness (§8.6) and the web login page.

**Not executed yet:** no Compose or CI change since v0.1.0 has run, because Docker is not on the
development host and nothing has been pushed. The first `compose-smoke` run after Stage 6 is the first
real test of the new images, the healthchecks and the Caddy service definition.

- A fresh development stack has no accounts. Create them with
  `docker compose exec api rackflow-admin seed-demo`; it prints a generated password once.
  `RACKFLOW_SEED_PASSWORD` is not passed to containers by Compose.
- Containers get only the settings listed under `x-backend-env`: now also `VECTOR_STORE_API_KEY`
  (empty = no key), `MODEL_TIMEOUT_SECONDS` and `WEB_PROXY_TIMEOUT_SECONDS`. The retrieval and chunking
  settings still do not reach them.
- `web` has the fixed address 172.30.0.10, `caddy` 172.30.0.11, on subnet 172.30.0.0/24 with
  `ip_range` 172.30.0.128/25. If that overlaps a host network, change the subnet, both addresses and
  `TRUSTED_PROXY_IPS` in `deploy/compose.prod.yml` together.
- Healthchecks: the API probes `/api/v1/health/live`; the web image has its own HEALTHCHECK (a fetch of
  `/`), so `up --wait` now waits for web; the worker and migrate disable the backend image's check.
- Images (Stage 6): backend is two-stage (`python:3.12.16-slim-trixie`, uv 0.12.22, `uv sync --frozen
  --no-dev`), web three-stage (`node:24.22.2-alpine3.24`, npm/npx/corepack removed). Both run as UID/GID
  10001 with code owned by root. They use BuildKit cache mounts, so build with Compose v2 or buildx.
  Checked with hadolint 2.12.0 and a build-context script; **not built here**.
- The web image bakes the API proxy target (`API_PROXY_TARGET`, default `http://api:8000`) and the proxy
  timeout (`API_PROXY_TIMEOUT_MS`, §8.9) at build time.

Scale workers with `docker compose up --scale worker=3` (documented; queue concurrency is covered
by tests, not by a multi-replica Compose run).

- Requires Compose 2.24.4+ (`!reset`), DNS for `DOMAIN`, and ports 80/443 reachable.

### 8.5 Database migrations and rollback
- Apply: `alembic upgrade head` — verified (local, CI, clean install).
- Roll back one revision: `alembic downgrade -1`; to empty: `alembic downgrade base` — the full
  `upgrade head → downgrade base → upgrade head` round trip is an automated test.
- Before production migrations take a database backup; downgrades drop the affected tables.

### 8.6 Health probes and operations
- Liveness: `GET /health/live` (also `/api/v1/health/live`). It is `async` and touches no dependency,
  so a slow database, Qdrant or model load cannot fail it; use it for restart decisions only.
- Readiness: `GET /api/v1/health/ready` returns 200 `{"status":"ready"}` only when every check is
  true, otherwise 503 `not_ready`. The body is booleans only (no counts, names or tenant data):
  - `database`: one query (does any chunk of a live indexed document exist?) inside a transaction with
    a 2 s statement timeout;
  - `vector_store`: one Qdrant `count` on a probe client with a 3 s timeout;
  - `vector_collection`: the configured collection exists, or nothing is indexed yet (the worker creates
    it on the first index, so a fresh install is ready);
  - `vector_collection_consistent` (new in Stage 6): when live indexed chunks exist, the collection
    exists and holds at least one point;
  - `embeddings`: the embedding provider embeds a short string within 5 s; success is cached for 60 s.
    The API loads the model in the background at startup; on a cold model cache readiness stays 503
    while it downloads.
  Monitoring that compares the exact check keys must include `vector_collection_consistent` (ADR-031).
- Lost vectors (a deleted collection, or one recreated empty: readiness shows
  `vector_collection_consistent: false` and logs `readiness_vector_collection_inconsistent`): rebuild
  them from the stored originals with `rackflow-admin reindex --tenant <slug> [--include-failed]
  [--dry-run]`, then let the workers drain the queue. Re-index jobs run behind interactive uploads
  (priority 200).
- Jobs that fail because a library cannot be loaded on the host (ImportError, DLL load errors)
  fail at once with `DEPENDENCY_UNAVAILABLE` instead of being retried; fix the host, then retry.
- Partial loss is still not detected: a collection lost, recreated by `ensure_collection` and then given
  new uploads has points again, so readiness goes green while older documents have no vectors. The probe
  does not compare point and chunk counts (they legitimately differ during reindex and delete). Watch for
  the `vector_collection_created` warning.
- `reindex --include-failed` skips documents whose newest job is a failed or cancelled delete and prints
  them as skipped, including in a dry run. A document the owner retried after a failed delete is still
  re-indexed.
- Evaluation runs hold a worker. On a rate-limited model a 13-question run can take minutes (about a minute measured on Groq's free plan),
  and with one worker uploads queue behind it. To separate them, run a dedicated worker:
  `python -m rackflow.worker.main --job-types evaluation_run`, and give the other workers
  `--job-types ingest_document,delete_document`. The retry itself has not been run against a real
  rate-limited provider.
- Worker liveness: heartbeats every 5 s in `worker_heartbeats`; the console marks a worker stale
  after 15 s. A crashed worker's jobs are reclaimed after `JOB_LEASE_SECONDS` (verified by a
  process-kill test).
- Logs: JSON lines on stdout with correlation IDs; no document text, prompts or answers.

### 8.8 Load balancers and client addresses (`TRUSTED_PROXY_IPS`)
Sign-in and demo rate limits are per client address. The API takes that address from the connecting
peer, and trusts `X-Forwarded-For` only from peers listed in `TRUSTED_PROXY_IPS` (ADR-025).

**Production (Stage 6, ADR-028): Caddy is the load balancer.** The chain is

```
client --HTTPS--> caddy 172.30.0.11 --> web 172.30.0.10 (Next /api rewrite) --> api :8000
```

1. **Caddy** has no `trusted_proxies`, so it ignores any `X-Forwarded-For` a client sends and sets the
   header to the client's real address.
2. **Web** passes the header on unchanged and adds nothing.
3. **The API's** peer is web. The overlay sets `TRUSTED_PROXY_IPS=172.30.0.10,172.30.0.11`, so the API
   reads the header from the right and rate-limits by the real client. `172.30.0.10` is required;
   `172.30.0.11` is defensive, in case the web proxy ever appends its own peer.

Rules: do not trust anything else (not the gateway `172.30.0.1`, not the subnet); never publish ports
3000 or 8000 while this is set; add `trusted_proxies` to the Caddyfile only if another load balancer
sits in front of Caddy, and then only its exact addresses. If Caddy's access log shows `172.30.0.1` for
every client, Docker's userland proxy hides client addresses and all clients share one bucket again
(`deploy/README.md`). Checked with `ratelimit.client_ip` unit calls for this list; **not executed through
a real Compose network.**

Development (no overlay): leave `TRUSTED_PROXY_IPS` empty. All Compose traffic then shares the web
container's address, so one client can use up the sign-in limits for everyone. This is acceptable only
while port 3000 is bound to loopback, as it is by default. With some other load balancer in front of
web, make it set `X-Forwarded-For`, set `TRUSTED_PROXY_IPS=172.30.0.10`, and make port 3000 reachable
only through it.

Values are comma-separated IP addresses or CIDR ranges. Startup refuses `*`, hostnames and `/0`. Next's
pass-through behaviour was checked with a throwaway `next dev` app and an echo server; `next start` was
not tested for this.

### 8.9 Timeouts (ADR-032)
| Setting | Read by | Default | Rule |
| --- | --- | --- | --- |
| `MODEL_TIMEOUT_SECONDS` | API | 60 s (max 600) | Production refuses it unless below `WEB_PROXY_TIMEOUT_SECONDS` |
| `WEB_PROXY_TIMEOUT_SECONDS` | API, worker, migrate | 120 s (max 3600) | Whole seconds in Compose |
| `API_PROXY_TIMEOUT_MS` | web, at **build** time | 120000 | Compose derives it as `${WEB_PROXY_TIMEOUT_SECONDS}000`; `next.config.ts` refuses a non-positive or non-whole value, and one not above `MODEL_TIMEOUT_SECONDS`×1000 when that is set in the build environment |
| `CADDY_UPSTREAM_TIMEOUT` | caddy | `180s` | Keep above `WEB_PROXY_TIMEOUT_SECONDS`; raise by hand above about 170 s |

A new value needs `--build`, because the standalone web server bakes it in. Outside Docker, set
`API_PROXY_TIMEOUT_MS` = `WEB_PROXY_TIMEOUT_SECONDS`×1000 yourself. The anthropic client retries once and
the chat provider can wait 10 s for a concurrency slot, so the real worst case is about
2×`MODEL_TIMEOUT_SECONDS` + 10 s + retrieval: keep a wide margin.

### 8.10 Accounts in production (ADR-029)
- First admin per tenant: `rackflow-admin bootstrap-admin --tenant <slug> --tenant-name <name> --email
  <email> [--name <display>] [--password-env RACKFLOW_ADMIN_PASSWORD]`. Unset variable → a generated
  password printed once. Exit 2 if the tenant already has an org_admin, on a weak password, a bad email or
  a bad slug. Audited as `member.bootstrap_admin`. An existing account becomes admin with its password
  unchanged.
- `seed-demo` and `seed-eval` exit 2 with `APP_ENV=production` unless `--allow-in-production`.
  `seed-infra` has no such guard (simulated racks only).
- CLI password policy (`bootstrap-admin`, `create-user`, `seed-demo`): 12 to 512 characters, not common,
  no `password`/`qwerty`/`123456`/`rackflow` fragments, at least 5 distinct characters, no email name.
  Passwords set through the admin API are not checked against it.
- Demo sign-in is off in production even if `DEMO_MODE` were forced on (`demo_enabled()`).

### 8.11 Backup, restore and the restore drill (ADR-030)
Full procedure: `scripts/ops/README.md`. Summary:

- `python scripts/ops/backup.py --output <dir> [--keep N] [--env-file .env]` writes
  `rackflow-backup-<UTC ts>/` with `postgres.dump` (`pg_dump -Fc`), `qdrant.snapshot`, `objects.tar.gz`
  and `manifest.json` (sizes, sha256, tool and server versions, Alembic revision, every table's rows,
  chunk and point counts, object counts). Needs PostgreSQL client tools (`PG_BIN` or `PATH`) at least as
  new as the server. Exit 0 / 1 / 2.
- Under the production overlay, PostgreSQL and Qdrant are not published: add a host-only
  `compose.backup.yml` with `127.0.0.1:5432` and `127.0.0.1:6333` (not verified here).
- **Retention:** `--keep N` deletes the oldest backups beyond the newest N, and only directories this tool
  wrote. Example: nightly with `--keep 14`. Copy backups off the host, encrypted (not done by the tool).
  Backups hold password and session-token hashes and every tenant's documents; on POSIX they are 0700/0600.
- `python scripts/ops/restore.py <backup> [--target-db] [--target-collection] [--target-storage]
  [--force] [--chown UID:GID]`: verifies every checksum first, refuses non-empty targets without
  `--force`, then prints a backup-vs-restored table. Exit 0 all match, 3 mismatch, 1 failure or refusal,
  2 bad arguments. Under the production overlay restore over the original names with
  `--chown 10001:10001` (`scripts/ops/README.md`, "With Docker Compose").
- **Restore drill:** before go-live, monthly, and after any PostgreSQL or Qdrant upgrade. Back up, restore
  into `rackflow_restore_drill` (database and collection) and a scratch directory, expect exit 0, then drop
  them. **Last drill: 2026-11-07 on the local Windows stack** (PostgreSQL 18.6, Qdrant 1.20.0): 25 tables,
  7,652 rows, 9 points, 9 files, every count matched; a second run without `--force` was refused for all
  three targets. Not run against Docker volumes, on Linux, or against a Qdrant with an API key.
